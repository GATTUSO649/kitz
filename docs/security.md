# Security status

Implemented protections include validated environment configuration; Helmet headers; exact-origin CORS and Origin checks on customer authentication, account, and order mutations; bounded JSON requests; API and authentication rate limits; Zod input validation; parameterized Drizzle queries; redacted request logging; and generic production error responses. Customer and administrator passwords use bcrypt hashes. Session tokens are random opaque values stored as SHA-256 digests and sent in HttpOnly, SameSite=Strict cookies; cookies are Secure when `NODE_ENV=production`.

Administrator API routes require an authenticated administrator session. First-administrator setup and verification are restricted to local development. The application has an administrator audit log. Product image uploads enforce an 8 MB limit and JPEG/PNG/WebP signatures before upload. Daraja callbacks require a secret path token, query the provider, and validate order, amount, phone, currency, and transaction time before marking a payment successful. These controls have unit coverage, but the database-backed callback flow has not been fully tested end to end.

This is not a launch security review. Customer email verification and password recovery, role-based administrator permissions, broader privacy/data-retention workflows, tested backups and restores, payment/order expiry operations, monitoring/alerting, and end-to-end production tests remain incomplete. Image signature checks do not replace image re-encoding or malware scanning. Dependency audit and unit tests are useful checks, not proof that the application is secure. Do not accept live orders, expose customer data, or process production payments until the remaining controls are reviewed and tested.

For deployment, use dedicated least-privilege MySQL accounts and verified TLS, managed secrets, HTTPS, tested backups, monitoring, and continuous dependency scanning. Rotate any credentials that have ever been committed or shared.
